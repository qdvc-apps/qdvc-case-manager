## 1. User request

QDVC Case Manager is to be a Mac app built with Swift that supports the allocation of cases to a pool of analysts.

* CASE CATALOGUE: The list of cases ("case catalogue"), is ingested from a CSV export from a legacy system. Amongst its many columns are case ID, case title, case genre, and case registration date. These columns are not named nicely from upstream so the CSV will need to be mapped.
* ALLOCATION CONTROL SHEET: Regular case allocations are performed on another system, which also provides a CSV export ("allocation control sheet"). Amongst its many columns are case ID, case title, case genre, case registration date, allocation supervisor, allocation date, allocation outcome, allocation note, allocated analyst.
   * The case title, case genre, and case registration date from this file should in theory match the details from the case catalogue; where they do not match, defer to the case ID as the authoritative identifier, but flag the issue as a (!) in the UI against that case's record.
   * There are a handful of allocation supervisors. They allocate the case either to an analyst (allocation outcome "a" for "allocated analyst") or they determine that the case should not proceed any further, but instead be refused and returned to sender (allocation outcome "r" for "refused & returned"). Note that there may also be non-standard allocation outcomes, e.g., "Operation Waymaker". These should be handled appropriately.
   * The allocated analyst is written in shorthand. There needs to be a place in the UI where the shorthand is mapped out to the analyst, including their full name and a long string describing their areas of specialisation/expertise.
   * The allocation note is EITHER - in the case of "a" (allocated analyst), a substring from the analyst's specialisation/expertise string - OR - in the case of "r" (refused & returned), the name of one of the return-to-sender message templates (e.g., IS_DUPLICATE, INCOMPLETE_FORM, UNAUTHORISED_ENTITY_REV23, INSUFFICIENT_FUNDS, OUT_OF_SCOPE, CODENAME_JUNO, CODENAME_NEPTUNE). In some cases the "a" allocation note is a special note (e.g., "As per Protocol 67", "Analyst is Team Leader for Operation Waymaker"), etc.
* DECISION SUPPORT FOR A SELECTED CASE: for a selected case the user, an allocation supervisor, can double click into it and see a decision support screen about which analyst to allocate. The allocation supervisor must take into account analyst workload over time, which is already something tracked by this app (see "WORKLOAD MANAGEMENT" below). The allocation supervisor on a separate screen is going to be looking at the case details and paperwork. So, this part of the app should give the user (allocation supervisor) a way to search/filter through the specialisations/expertise strings of the analysts to narrow down a few options, with the metrics of the shortlisted analysts (workload this month, workload past 12 months) shown. 
* PROJECT WORKSHEETS: Sometimes a series of cases pertain to a particular project, operation, or special event, e.g., "Operation Waymaker". These are still present in the case catalogue and allocation control sheet. However, the project's captain / team leader / principal analyst (the terminology differs between projects, essentially the analyst designated leader) will supply their own "project worksheet" exported as CSV. These are ingested for oversight and completeness. There are no guarantees about the structure of these project worksheets apart from columns being attributes, rows being records, and the case ID being one of the columns. The presence of a case on a project worksheet should be indicated in the main case catalogue view.
* WORKLOAD MANAGEMENT: in order to ensure an equitable balance of workload, QDVC Case Manager provide a dashboard showing the analysts total workload of cases over time. The current spreadsheet based system has a simple pivot table where the columns are months and the rows are analysts, and the cells are count per month per analyst shaded with a conditional formatting heat map. This is still desirable, but we also want to see more insights on the dashboard.
* ACCEPTANCE RATES AND REFUSAL RATES: the current spreadsheet based system also has a simple pivot table showing the number of cases with an "a" outcome versus an "r" outcome, month by month, in terms of "acceptance rate" ( = a/(a+r) ) and  "refusal rate" ( = r/(a+r) ).


Data is stored in a "workspace" folder and Git-tracked elsewhere, so data storage is designed to accommodate for this. YAML is the preferred data structure, supplemented by CSV where it makes sense.
